# Rule: TDD 強制（Red → Green → Refactor）

**黄金律：テストが設計を駆動する。失敗するテストが存在する前に実装を書かない。**

## Red フェーズ
- [ ] 失敗するテストを先に書く（未実装の関数/振る舞いを参照）。
- [ ] 実行して**失敗**を確認した（PHPUnit / Vitest / Playwright）。
- [ ] 実装コードはまだ書いていない。
- [ ] コミット：`test: <feature> の失敗テストを追加`

## Green フェーズ
- [ ] テストを通す**最小**実装のみ（リファクタ・余計な機能なし）。
- [ ] テストを書き換えて通していない（テストは仕様）。
- [ ] 対象テストが**成功**、既存テストも回帰なし。
- [ ] コミット：`feat: <feature> を実装`

## Refactor フェーズ
- [ ] 重複除去・命名・抽出など構造改善のみ（振る舞い不変）。
- [ ] 全テスト緑、静的解析（PHPStan/PHPCS または tsc/eslint）も緑。
- [ ] コミット：`refactor: <area> を整理`（純粋な機械的整理は `tidy:`）

## アンチパターン（見つけたら停止）
- ❌ 失敗テストなしの実装先行
- ❌ 実装ではなくテストを書き換えて通す
- ❌ 1 コミットに複数フェーズ / 複数 ToDo を混在
- ❌ テストを実行せずに「通った」と主張
- ❌ 振る舞い変更と構造変更を同一コミットに混在

## 規律
- **1 ToDo = 1 BDD シナリオ = 1 Red サイクル**。進捗は Plan ファイルの `- [ ]`/`- [x]`。
- 実装は `tools/check_tdd.sh` により「src 変更にはテスト随伴」を強制（pre-commit）。
- 実装エージェントは **2 連続 Red で停止 → `failure-analyst`** へ。
- t-wada：「一度に 1 アサーション、一度に 1 テストケース、テストの TODO リストで設計を駆動する」。
